# Восстановление после отказа кодировщика — 0.3.7-beta.3

В сообщении пользователя QSV не смог создать MFX session (`-9`), FFmpeg завершился до первого выходного пакета. Нельзя по этой строке однозначно различить отсутствие подходящего GPU, отключение графики или проблему драйвера/runtime. Наличие `h264_qsv` в списке FFmpeg не гарантирует возможность запуска: [FFmpeg отмечает зависимость runtime-доступности от оборудования и драйвера](https://ffmpeg.org/ffmpeg.html).

До исправления supervisor повторял выбранный QSV без изменения параметров, передача не запускалась. В 0.3.7-beta.3 после ошибки FFmpeg проверяется наблюдавшаяся диагностика инициализации конкретного аппаратного кодировщика. При распознанной ошибке QSV/NVENC/AMF текущий pipeline переходит на libx264; на следующем запуске заново строятся аргументы с прежними источниками и настройками качества. Выбор пользователя в конфигурации не переписывается. Для повторной попытки аппаратного кодирования нужно заново запустить pipeline, например сохранить CPU, затем снова выбранный аппаратный кодировщик.

Переход однократный для данного pipeline. Ошибки запуска самого FFmpeg, WASAPI, экрана и сети не являются основанием для смены кодировщика. Список диагностик не исчерпывает все возможные ошибки всех GPU: неизвестные ошибки сохраняют прежний путь журналирования/повторов. Нагрузка на CPU при переходе может увеличиться; автоматического изменения разрешения/битрейта этот выпуск не добавляет.

В API pipeline добавлены `requestedEncoder` и `encoder`; интерфейс показывает фактически выбранный путь выполнения рядом с настройкой кодировщика. В журнале есть отдельное сообщение о переходе на CPU.

Проверки:

- На этом ПК реальный `h264_qsv` не смог запуститься; исправленный pipeline перешёл на x264 и получил 464 видеопакета TS и 12 AAC-пакетов за ~1,95 с от начала теста. Это проверка восстановления потока, не измерение задержки OBS.
- Выбранный `h264_qsv` в конфигурации сохранился, эффективный кодировщик стал `libx264`, сообщение о переходе появилось один раз.
- Повторно прошёл живой тест двух обрывов WASAPI: после каждого восстановились AAC-пакеты.
- Проверены реальные строки QSV из сообщения пользователя, примеры NVENC/AMF, разделённая на два чтения stderr строка и отрицательные примеры ошибок экрана, WASAPI и libx264.
- `go test ./...`, `go vet -unsafeptr=false ./...`, `node --check assets/app.js` проходят. Проверка unsafe.Pointer отключена для прежней Windows COM ABI-обвязки.

Аппаратные NVENC/AMF в этом испытании не запускались. Исправление не доказывает устранение проблем со звуком выбранного выхода на удалённом ПК или задержки отображения OBS.
