# Независимая проверка аудита от 19.11.2026

Проверены `docs/AUDIT_2026-11-19.md`, исходники исходной версии 0.3.4-beta
(HEAD `87e65a6`), OBS 30.1.2 и установленный FFmpeg 9.0.2. Исходный отчёт и
пользовательские файлы `tools/latencyprobe/` сохранены локально без изменений; исходный аудит и его оснастка не включаются в публичный репозиторий.
Исправления ниже подготовлены в тестовой сборке 0.3.5-beta.

## Основной вывод

Аудит обнаружил настоящие дефекты аудиозахвата, но его заключение
«задержка всей цепочки 350–500 мс, а 1–2 с вызваны только обрывами» **не доказано**.
Измерение темпа MPEG-TS не измеряет задержку от экрана презентера до OBS.
Нельзя исключить захват, очереди FFmpeg, декодирование и отображение.
Причина наблюдаемых пользователем рывков пока не локализована окончательно.

Несколько предложенных готовых правок ошибочны и не должны переноситься буквально:

- `fifo_size=25000` означает 25 000 пакетов по 188 байт: **4 700 000 байт**,
  примерно 6,27 с *ёмкости* при 6 Мбит/с. Это не 25 KB и не обязательная задержка.
  `fifo_size=1000000` выделяет около 188 MB. [FFmpeg UDP](https://ffmpeg.org/ffmpeg-protocols.html#udp)
- `async=1000` — предел плавной компенсации в сэмплах **в секунду**, а не
  21 мс допустимой ошибки. `max_hard_comp` отсутствует в установленном FFmpeg;
  предложенный фильтр с ним не запускается. `min_hard_comp` по умолчанию уже 0,1 с.
  Проверено также через `ffmpeg -h filter=aresample`.
  [FFmpeg resampler](https://ffmpeg.org/ffmpeg-resampler.html)
- `uintptr(100*time.Millisecond)` передаёт WASAPI **10 секунд**, а не 100 мс:
  API принимает единицы по 100 нс. В исправлении используется деление на 100 нс.
  [IAudioClient::Initialize](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-initialize)
- `SetEventHandle` имеет индекс **13** в vtable `IAudioClient`, а не 6.
  Метод 6 — `GetCurrentPadding`. Предложенный вызов нельзя применять.
  [Windows SDK Audioclient.h](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/Audioclient.h)
- Наличие предупреждения о недостаточном числе кадров для оценки частоты
  само по себе не доказывает причину последующего `I/O error` SRT.

## Проверка каждого пункта

| Пункт | Вердикт и действие |
|---|---|
| F-01 OBS buffer 0 | Частично подтверждён: выставляется `AVFMT_FLAG_NOBUFFER`. Однако ненулевой `buffering_mb` задаёт также протокольный `buffer_size`; утверждение «32 KB вместо 2 MB AVIO ⇒ обрывы» не доказано. Настройка оставлена прежней до сравнительного теста отображения. |
| F-02 probing SRT | Параметры действительно такие. `analyzeduration=0` означает автоматический выбор, а не нулевой анализ. Связь с периодическими разрывами не доказана. В новой схеме релеям вообще не нужен анализ кодеков: они переносят исходные байты через data demux/mux. |
| F-03 UDP socket capacity | Не была явно задана; конкретные фактические 64 KB не измерены. Добавлены `SetReadBuffer`/`SetWriteBuffer` по 4 MiB с журналированием ошибки установки. Это ёмкость, не целевая задержка. |
| F-04 FIFO | Расчёт в аудите неверен в 188 раз. Увеличение до миллиона пакетов отклонено. |
| F-05 VBV | Настройка подтверждается, ухудшение качества/пропуск кадров не измерены. Увеличение VBV без теста нагрузки не применено. |
| F-06 Render Delay | `maxDelay-estimate` — корректное выравнивание быстрых источников по медленным; замена на `estimate` нарушила бы его. Исправлен отдельный дефект: зритель без источника больше не увеличивает `maxDelay`. Для единственного источника автозадержка равна нулю. |
| F-07 лишняя тишина | Подтверждён дефект логики: пустой опрос добавлял 10 мс, а следующий реальный пакет мог покрывать тот же интервал. Вместо удаления всей тишины создана общая временная шкала с заполнением только недостающих кадров. |
| F-08 блокирующий io.Pipe | Подтверждён. COM-поток больше не пишет в блокирующий pipe: копирует пакет в ограниченное хранилище и сразу продолжает обслуживать WASAPI. |
| F-09 буфер WASAPI | Нулевой параметр подтверждён; точные «20 мс» без GetBufferSize не установлены. Задана ёмкость 100 мс в правильных единицах. Это не ожидание заполнения буфера. |
| F-10 polling | Подтверждён. Пока оставлен опрос каждые 5 мс: безопасность аудиочасов обеспечена временной шкалой, а не числом срабатываний таймера. Event callback — отдельная оптимизация, неверный рецепт vtable отклонён. |
| F-11 timestamp | Подтверждён. Используется QPC первого сэмпла; при ошибке timestamp — позиция устройства, при discontinuity — повторная привязка. |
| F-12 resampler | Интерпретация и предложенный фильтр неверны. Сохранён рабочий `async=1000:first_pts=0`; для PCM добавлены wall-clock timestamps, чтобы после сброса устаревших кадров FFmpeg видел временной разрыв. Очередь PCM уменьшена с 512 до 8 пакетов. |
| F-13 mix format | Есть явная проверка поддерживаемых PCM-форматов. Отсутствие AUTOCONVERTPCM при запросе собственного mix format не является само по себе ошибкой; нет воспроизведения несовместимого устройства. |
| F-14 oversized packet | Проверка действительно завершает повреждённый захват. Пакет больше секунды при ёмкости 100 мс не показан; отключать защиту без разбора причины не стали. |
| F-15 adaptive SRT | Рост до 600 мс возможен. Асимметрия не доказывает ошибку: SRT согласовывает receive/peer latency. Текущие настройки пользователя не изменены; тест транспорта проведён отдельно при 150 мс без адаптации. |
| F-16 GOP | Подтверждён интервал около секунды. Сокращён примерно до 0,5 с (`max(1,fps/2)`) для более быстрого восстановления картинки. Это не доказательство снижения постоянной задержки на 0,5 с. |
| F-17 retry OBS | 1 с подтверждается; увеличение до 3 с способно удлинить восстановление. Оставлено прежнее значение. |
| F-18 counters | Добавлены forwarded/sendErrors и аудиосчётчики в API. Ошибка отправки UDP не называется измеренной сетевой потерей; missingFrames включает законную тишину простоя. Сетевые потери этим не измеряются. |
| F-19 health | До исправлений API уже отдавал `media.srtHealth`: effectiveLatencyMs и reconnects. Отдельного отображения в интерфейсе действительно нет. |
| F-20 gdigrab | Подтверждён используемый API. Темп близкий к real time не исключает постоянную задержку. Замена захвата/кодировщика требует проверки на презентере с движущимся экраном. |
| F-21 версии | Разные версии подтверждены. Переиспользование совместимого установленного OBS предусмотрено установщиком; принудительная замена OBS сама по себе не лечит звук. Для проверки аудиоправок необходимо обновить презентер. |

В OBS проверены исходники [obs-ffmpeg-source.c 30.1.2](https://github.com/obsproject/obs-studio/blob/30.1.2/plugins/obs-ffmpeg/obs-ffmpeg-source.c)
и [media.c 30.1.2](https://github.com/obsproject/obs-studio/blob/30.1.2/deps/media-playback/media-playback/media.c).
Значение по умолчанию анализа MPEG-TS проверено в
[FFmpeg n9.0.2 demux.c](https://github.com/FFmpeg/FFmpeg/blob/n9.0.2/libavformat/demux.c).
Семантика QPC и флагов пакета — в
[IAudioCaptureClient::GetBuffer](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer).

## Почему зонд аудита не подтверждает его цифры задержки

В предоставленном `tools/latencyprobe/TsProbe.cs` обнаружены ошибки:

1. При `p=off+5` это байт флагов adaptation field; PCR начинается с `off+6`.
2. 33-битное поле PCR base собирается в 32-битный `uint` и обрезается.
3. После `base*300+extension` частота равна 27 MHz, делить на 90 000 нельзя.
4. Принимаются PCR любых PID без выбора программы; rollover не обрабатывается.
5. Вычитание PCR из времени с запуска процесса не является абсолютной задержкой:
   начальное смещение media clock произвольно, особенно после remux.
6. Блокирующий UDP Receive без тайм-аута не завершится по duration при тишине.

Поэтому PCR-derived результаты этого зонда непригодны для приёмки.
Сравнение продолжительности TS с wall-clock полезно как проверка среднего темпа,
но не как проверка capture-to-display latency. Исходную оснастку не меняли.

## Выполненные проверки новой схемы

| Проверка | Результат одного прогона 19.11.2026 |
|---|---|
| Все стандартные Go-тесты | PASS |
| `go vet -unsafeptr=false ./...` | PASS; COM ABI сохраняет существующее исключение unsafe pointer |
| Блочная доставка, простой, возобновление, запоздавшие данные PCM | PASS; тишина и реальные данные больше не удваивают время |
| Медленный потребитель PCM и Close | PASS; хранение ограничено 250 мс, чтение разблокируется |
| Старый код: живой WASAPI + тихий тон 440 Hz | 4 с PCM за 3,991 с; 75/75 окон с тоном. Рывки за этот короткий прогон **не воспроизведены** |
| Новый код: тот же тест WASAPI | 4 с PCM за 4,019 с; 75/75 окон с тоном; lateFrames=0, skippedFrames=0 |
| Реальный gdigrab + WASAPI → H264/AAC → TS → decode | PASS: 59 видеокадров / 4,000 с; 189 AAC-кадров / 4,032 с; разница start_time 21,3 мс |
| Два новых FFmpeg-релея UDP→SRT→UDP, timestamped payload | 300/300 пакетов по 1316 байт побайтово совпали и сохранили порядок; p50=158,7 мс, p95=165,2 мс, max=179,8 мс при SRT 150 мс |
| SRT от настоящего MPEG-TS отправителя FFmpeg | PASS |
| Go fanout → два SRT-отправителя → два приёмника | PASS |
| Зритель с высоким RTT рядом с одним источником | PASS; зритель больше не добавляет Render Delay |

Транспортный тест измеряет только локальный UDP→SRT→UDP с двумя FFmpeg-процессами.
В нём нет захвата экрана, Wi-Fi другого ПК, буфера и рендера OBS. Его p95 нельзя
выдавать за задержку пользователя. Аудиотест короткий и не заменяет длительный
просмотр/прослушивание под нагрузкой. Единичные missingFrames могут означать
простой аудиоустройства, а skippedFrames — сознательный сброс старого времени
после ожидания кодировщика; эти значения не являются счётчиками потерь сети.

## Текущая система и оставшаяся приёмка

Во время проверки главный ПК работал на 0.3.4-beta с SRT 250 мс и adaptive=true.
Презентер сначала отсутствовал, затем появился на 0.3.3-beta.
OBS подтвердил PLAYING; скриншот источника показал экран с секундомером.
Синхронного исходного изображения с презентера нет, поэтому измерить по этому
скриншоту задержку нельзя. Настройки и запущенные версии автоматически не менялись.

Подготовлена сборка 0.3.5-beta. Для проверки исправлений WASAPI её нужно запускать
на **презентере**, а не только на главном ПК. Приёмка: минимум 10 минут движущегося
видео со звуком, одновременная съёмка исходного секундомера и OBS одной камерой,
проверка p50/p95 задержки, хлопка/вспышки, счётчиков и reconnects. Отдельно проверить
нагрузку CPU, переключение аудиоустройства и восстановление после разрыва сети.
До этого обещать устранение задержки 1–2 с и рывков именно на другом ПК нельзя.

Команды повторения (Go и FFmpeg/FFplay/FFprobe должны быть в PATH):

```powershell
go test ./...
go vet -unsafeptr=false ./...
$env:LB_TEST_MEDIA='1'
go test -v -run 'TestSRT.*RealFFmpeg' -count=1 -timeout 60s
$env:LB_TEST_AUDIO='1' # тихий тестовый тон и временная запись локального экрана
go test -v -run 'TestNativeWASAPILiveClock|TestWASAPILiveAVEncoding' -count=1 -timeout 40s
```
