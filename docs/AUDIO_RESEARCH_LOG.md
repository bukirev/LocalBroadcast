# Журнал исследования пропусков звука Local Broadcast

## 20 ноября 2026 · редкие провалы после стабилизации передачи

**Статус:** звук доходит до OBS. Пользователь слышит значительно меньше пропусков на тестовой сборке, но иногда они остаются. Сопоставления одного и того же сбоя на отправителе и приёмнике пока нет.

**Версии для воспроизведения.** Главный ПК работает на [0.3.8-beta.2](https://github.com/bukirev/LocalBroadcast/releases/tag/v0.3.8-beta.2). На презентере запущен эксперимент с меткой сборки 0.3.8-beta.3-test.1. Исходники по умолчанию содержат номер релиза; метку тестового EXE задавали через Go linker flag `-X main.appVersion=0.3.8-beta.3-test.1`. [Снимок исходников](https://github.com/bukirev/LocalBroadcast/tree/b6ff93a03fc762ea5c858a493d1b391da6d15cb0) · [изменения эксперимента](https://github.com/bukirev/LocalBroadcast/commit/b6ff93a03fc762ea5c858a493d1b391da6d15cb0) · [сравнение с релизом](https://github.com/bukirev/LocalBroadcast/compare/v0.3.8-beta.2...b6ff93a).

**Тракт.** На презентере WASAPI loopback захватывает системный звук. Кольцевой буфер хранит до 250 мс PCM, чтение отстаёт от часов захвата на 40 мс. Когда отставание от требуемой позиции превышает половину ёмкости, читатель перескакивает ближе к текущей позиции и увеличивает skippedFrames. PCM с метками времени поступает в FFmpeg через stdin в Matroska. Тот же процесс кодирует экран и звук. Рабочий профиль испытания — 1280×720, задано 60 FPS, libx264 2000 кбит/с, AAC stereo 48 кГц 128 кбит/с, MPEG-TS/UDP. Главный ПК — Pentium 5405U, четыре логических процессора, OBS 32.1.1. Настройка FPS задаёт цель захвата. Фактический FPS следует измерять отдельно.

**Что изменено.** Тестовая сборка выдаёт PCM пакетами по 10 мс вместо порций переменной длины; входная очередь FFmpeg увеличена с 8 до 32 пакетов. 320 мс — ёмкость при заполнении. Фактическое время ожидания зависит от загрузки. Изменения испытаны вместе, вклад каждого ещё предстоит разделить. Порог перескока внутри кольцевого буфера по-прежнему равен 125 мс. ## Следующие эксперименты

1. **Локализовать один провал.** Запустить непрерывный тон, записать время старта и расхождение часов ПК. В течение 15 минут одновременно сохранять приращения skippedFrames, missingFrames и deviceDiscontinuities на презентере, отметки WatchAudio и запись на главном. Для спорного эпизода сравнить декодированную копию исходящего потока и запись OBS вокруг одного маркера. При чистом исходящем потоке проверить непрерывность пакетов MPEG-TS по аудио PID на обеих сторонах. Промежуток без обновления шкалы обозначать отдельно.
2. **Проверить, где останавливается чтение.** Измерять интервалы чтения PCM, длительности записи в канал FFmpeg, фактическую частоту видео и загрузку CPU при том же сюжете. Сравнить исходный профиль, только фиксированные пакеты, только увеличенную очередь и текущую комбинацию. Не смешивать работу двух параллельных кодировщиков с одиночным рабочим запуском. Зафиксировать начальный прогрев отдельно.
3. **Проверить независимый аудиокодировщик.** Гипотеза: временная перегрузка видеотракта задерживает потребление PCM. В прототипе отделить чтение и кодирование аудио, сохранить общую временную шкалу и ограничить очереди до и после мультиплексора. Проверить синхронизацию при просадке FPS, переподключении, паузе и возобновлении системного звука. Простое увеличение буфера способно увеличить сквозную задержку.
4. **Проверить адаптивный приёмный буфер**, если исходящий поток цел, а входные пакеты запаздывают. Сравнить проводную сеть и Wi-Fi, измерить распределение опозданий и изменение A/V задержки при росте и уменьшении буфера. [Scream](https://github.com/duncanthrax/scream#functional-description) показывает независимую передачу коротких блоков PCM по UDP. [SonoBus](https://www.sonobus.net/sonobus_userguide.html) описывает управление приёмным буфером для каждого соединения. Оба проекта полезны для сравнения; синхронизацию с видео в OBS нужно проверить у нас.

**Команды.** На главном запустить скрипт из снимка исходников при работающих OBS и Local Broadcast. На презентере минутный тест создаёт дополнительный локальный поток, воспроизводит тон и временно захватывает экран и системный звук. Нужны работающий локальный API и доступные FFmpeg/FFplay.

```powershell
# Главный ПК, из каталога репозитория
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\obs-latency\Test-OBSDecoder.ps1 -Mode WatchAudio -Seconds 900
# Презентер, из каталога экспериментальной ветки
$env:LB_TEST_AUDIO_LONG = '1'
go test -v -count=1 -run '^TestPacketPCMLivePipelineConsumesForMinute$'
Remove-Item Env:LB_TEST_AUDIO_LONG
```

**Как дополнить журнал.** Добавьте датированную запись с хешем коммита, версиями обоих ПК, профилем, транспортом и длительностью. Для новой идеи укажите механизм, ожидаемый наблюдаемый признак, опыт для проверки и результат, при котором гипотезу следует отвергнуть. Для прогона приложите число и суммарное время провалов, самый длинный интервал, синхронизацию A/V и повторные замеры задержки. Публикуйте обезличенные показатели. Полный ответ API состояния содержит параметры доступа.
