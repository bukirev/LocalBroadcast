# Приёмка медиадвижка Windows

Пороговые значения зафиксированы перед аппаратным сравнением. На каждом ПК записать модель GPU, устройства, версии драйверов, версии программы и выбранные режимы. Сравнить с FFmpeg на тех же маршрутах и сцене.

| Испытание | Предварительный критерий |
|---|---|
| Экран и непрерывный контрольный тон 2 часа | 0 зависаний и провалов тона ≥100 мс после прогрева. Расхождение A/V ≤80 мс у 95% синхронных вспышек/щелчков. |
| UVC и HDMI 720p30, аудио при наличии | 10 мин на устройство. Согласованный режим подтверждён caps, дорожки декодируются, ≥29 FPS на движущемся тесте. |
| Два получателя, рестарт OBS, обрыв Wi-Fi и возврат USB | После восстановления доступности устройства/связи видео и звук возвращаются за ≤15 с. Второй получатель продолжает при рестарте первого. |
| Смена выхода Windows, тишина, снова тон | 60 с тишины без ложного цикла рестартов. Тон возвращается ≤5 с, явно выбранное устройство не подменяется другим. |
| Задержка, ресурсы | 30 одновременных снимков обоих экранов, p95 не хуже FFmpeg более чем на 50 мс. Рост за 2 часа ≤100 мс. Средняя загрузка CPU ≤ baseline + 10 процентных пунктов, прирост working set после прогрева ≤100 МиБ. |

Пороговые значения являются критериями испытания. Для приёмки нужны измерения обоих концов и физические устройства.

## Проверки 20 ноября 2026

- Windows x64: реальные d3d11screencapturesrc и wasapi2src loopback, 1280×720/30, mfh264enc и AAC; два UDP-получателя получили TS. FFprobe подтвердил H.264/AAC, средний уровень декодированного тона −54,6 дБ.
- Через штатные SRT relay и два SRT-приёмника: 2468 пересланных пакетов, sendErrors=0, декодированный тон −58,5 дБ. Проверки длились 12 секунд. Штатный libsrt доступен через поставляемый FFmpeg.
- Воспроизведение: установить LB_TEST_GST_CAPTURE=1 и запустить go test -run TestGSTScreenOnWindows -v -count=1. Добавить LB_TEST_GST_SRT=1 для SRT. gst-launch, ffplay, ffprobe, ffmpeg должны быть в PATH. Тест временно захватывает экран и воспроизводит тихий тон.
- Длинный прогон запущен на рабочем презентере с отдельной копией конфигурации, на профиле 720p60. Пишется CSV с PID, CPU, RAM, уровнем до кодирования, актуальностью аудиобуферов и числом переданных пакетов. Критерий мелких провалов требует параллельной диагностики на главном OBS. Значение peak за 500 мс до кодирования не обнаруживает каждый провал длиной 100 мс.
- Физические USB-веб-камера и HDMI-плата отсутствуют. Смена аудиоустройства, принудительный обрыв Wi-Fi, перезапуск OBS и контроль A/V вспышкой/щелчком остаются отдельными сценариями.

Для повторения длинного прогона выберите нужный движок в настройках, запустите передачу на получателя и выполните в PowerShell:

```powershell
.\tools\gst-lab\Measure-Presenter.ps1 -Backend gstreamer -Seconds 7200 -FFplay C:\LocalBroadcast\ffplay.exe -OutputCsv .\gst-presenter.csv
```

Для сравнения повторите с FFmpeg и новым именем CSV. В скрипте измеряются процесс захвата, объём переданного потока и телеметрия до кодирования. На главном ПК выполните четыре последовательных запуска WatchAudio по 1800 с, сохранив JSON для каждого запуска. Укажите точное время начала каждого измерения, смещение часов ПК и эпизоды, которые были слышны. A/V-синхронизацию и сквозную задержку измеряйте одновременной съёмкой импульса и изображения на обоих концах.
