# Испытания 0.3.6-beta и исправления аудиозахвата

Дата: 19 ноября 2026. Исходный релиз: `v0.3.6-beta` (`4f8d4d7`).
Статус: дефект аудиовремени воспроизведён и исправлен в исходниках. Причина значительной части видеозадержки локализована в приёмнике OBS. Снижение полной задержки между двумя физическими ПК ещё не подтверждено.

## Условия и границы измерений

Windows 10 22H2, 28 логических CPU, GTX 750 Ti, OBS 30.1.2 / WebSocket 5.4.2, FFmpeg 9.0.2, Go 1.27.4. Основной ПК и подключённый презентер работали на 0.3.6-beta. Heartbeat RTT до презентера около 1 мс; установленная SRT latency 250 мс. Heartbeat RTT не является замером медиазадержки.

Для лабораторных испытаний использованы отдельные локальные UDP/SRT-порты, настоящие `Pipeline.forwardLoop`, `startSRTSender` и `startSRTReceiver`. В OBS создавалась временная сцена только в Preview. Program, запись и трансляция не переключались. По завершении Preview восстановлен, временные сцены удалены, affinity OBS восстановлена на все 28 CPU (`268435455`). Рабочий источник `LB | Presenter` сохранён: UDP:5000, MPEG-TS, buffering_mb=0, audio offset=0.

Это испытания на одном ПК. Они не измеряют физический экран второго ПК, сеть под нагрузкой и задержку звукового устройства слушателя. Сырые записи рабочего стола и системного звука хранятся только локально в `.tools`, в релиз их включать нельзя.

## Звук: подтверждённый дефект

В 0.3.6 каждый QPC timestamp пакета WASAPI независимо округлялся до номера сэмпла. При этом счётчик устройства показывал непрерывные пакеты. Округление создавало вставки тишины и перекрытия по одному сэмплу.

Один и тот же захват: 2404 пакета, все 2403 перехода непрерывны по device position. После старого преобразования QPC: 1656 непрерывных переходов, 390 пропусков по 1 сэмплу, 356 перекрытий по 1 сэмплу, один пропуск 2 сэмплов. После исправления все 2403 перехода непрерывны.

Исправление: позиция каждого непрерывного пакета берётся из точного счётчика устройства. QPC привязывает начало и медленно оценивает частоту устройства. Часы чтения следуют этой частоте без вставки/удаления отдельных сэмплов. После реального разрыва выполняется новая привязка. Кольцевой буфер по-прежнему ограничен 250 мс, рабочая выдержка 40 мс.

Контрольный сигнал — синус 1 кГц, WASAPI float32 stereo 48 кГц. SNR здесь — оценка относительно синуса, подобранного методом наименьших квадратов по окнам 100 мс; это сравнительная диагностика, а не оценка качества речи/музыки или сертифицированный SINAD.

| Испытание | 0.3.6 | Исправление |
|---|---:|---:|
| До временной шкалы, захват одних и тех же пакетов | 73,72 дБ | 73,72 дБ |
| После временной шкалы, тот же сигнал | 24,63 дБ | 73,72 дБ |
| Реальный gdigrab 1080p30 + WASAPI, PCM перед AAC, медиана | 24,95 дБ | 66,35 дБ |
| Тот же 30-секундный прогон, после AAC 128 кбит/с и декодирования | 23,18 дБ | 49,51 дБ |
| После AAC, 5-й процентиль | 19,91 дБ | 49,35 дБ |

Для последнего сравнения базовый исходник извлечён из тега 0.3.6, добавлен только диагностический тест. В обоих вариантах видео около 30 с, AAC 30,037 с; анализ центральных 2–28 с исключает запуск/остановку. Различие абсолютного SNR двух серий связано также с уровнем тестового тона; сравнивать надо строки внутри каждой серии.

Отдельно проверены три варианта timestamp для синтетического PCM (20 с каждый): wallclock, sampleclock, sampleclock с asetpts. Результаты одинаковы, SNR около 58 дБ: гипотеза, что достаточно убрать wallclock timestamps, не подтвердилась.

Один первый прогон старого кода завершил аудиозахват около 4,7 с. Повтор с журналированием отработал полные 30 с без ошибок. Причина единичного завершения не установлена; считать её исправленной нельзя.

## Видео: сеть не объясняет всю секунду

Генератор 640×360, 30 fps кодирует номер кадра двоичными метками. Время генерации сопоставляется с кадром, возвращённым `GetSourceScreenshot` OBS. Первые 5 с исключены. Таблица показывает медиану/95-й процентиль середины интервала запроса; запрос обычно занимал 27–29 мс. Это измерение до рендера источника OBS, не до физического дисплея.

| Тракт | Медиана | p95 |
|---|---:|---:|
| H.264 + AAC → UDP → OBS, исходные настройки | 1004 мс | 1022 мс |
| H.264 + AAC → SRT 250 → OBS, исходные настройки | 1159 мс | 1172 мс |
| H.264 + AAC → SRT 250, buffering_mb=2 + probe 100 мс | 962 мс | 978 мс |
| H.264 + AAC → UDP, OBS на всех 28 CPU | 1008 мс | 1027 мс |
| Тот же тракт, OBS временно ограничен 2 CPU | 501 мс | 522 мс |
| H.264 без аудио → UDP, 28 CPU | 640 мс | 661 мс |
| H.264 без аудио → UDP, 2 CPU | 228 мс | 245 мс |
| MPEG-4 Part 2 + AAC → UDP, buffering=2/probe=100 мс | 257 мс | 279 мс |
| MPEG-4 Part 2 + AAC → SRT 250, buffering=2/probe=100 мс | 502 мс | 516 мс |

В отдельном `-debug_ts` прогоне время генерация → mux пакета H.264 составляло около 0,5 мс. Локальный тест двух настоящих SRT-процессов при latency=150 мс: 300/300 датаграмм побайтово совпали; p50=158,6 мс, p95=165,8 мс, max=180,3 мс. Этот тест исключает кодеки и OBS и не моделирует потери Wi-Fi.

Исходники OBS объясняют эффект числа CPU: декодер H.264 получает `thread_count=0` (автоматический выбор), а MPEG-4 Part 2 сохраняет один поток. Уменьшение affinity — только диагностический эксперимент: применять его постоянно нельзя без проверки влияния на запись, рендер и остальные источники.

1080p с движущейся областью также проверено, но screenshot RPC занимал 216–408 мс, существенно влияя на погрешность и нагрузку. Эти цифры не подходят для точного сравнения: PNG дал примерно 1215/686 мс (H.264/SRT250 против MPEG-4/SRT150), BMP — 1365/888 мс. Разные SRT latency и большой интервал запроса не позволяют приписать разницу только кодеку. Нельзя обещать 1080p <500 мс на основании теста 640×360.

## Что не следует менять вслепую

- Аппаратное декодирование само по себе не устранило секунду: H.264/UDP около 916 мс.
- Уменьшение probe или SRT latency само по себе не решило задержку. Probe 1 мкс может нарушить обнаружение аудио и не выбран рабочим значением.
- `full_decode=true` в проверке не дало изображения; вариант отвергнут.
- `threads=1` в `ffmpeg_options` Media Source не является проверенным способом управлять decoder threads: OBS передаёт эти options в открытие формата, а codec открывает отдельно.
- В просмотренном коде OBS 33 сохранён тот же выбор decoder threads; обновление OBS само по себе не доказано как решение.
- MPEG-4 не переключён в продукте по умолчанию. В сравнении одного 8-секундного `testsrc2` 1080p30 при около 6 Мбит/с SSIM H.264=0,991306, MPEG-4=0,983191 (битрейт файлов 6,161/6,078 Мбит/с). Это подтверждает компромисс качества; одного синтетического сюжета недостаточно для выбора кодека для рабочего стола/текста.

## Проверки и воспроизведение

`go test ./...` проходит. Тесты часов проверяют 10000 пакетов с QPC jitter, реальный разрыв и моделируемый час при ±200 ppm: ошибка очереди <10 сэмплов, оценка частоты отличается <0,02 Гц. Моделируемый час не является часовым аппаратным прогоном.

Живой `TestWASAPILiveAVEncoding` проходит: 60 кадров/4,000 с, AAC 4,032 с, разница начала 21,3 мс, lateFrames=0. Начальные missing/skipped учитывают запуск и подготовку кодера; их нельзя объявлять потерями в установившемся воспроизведении без привязки ко времени.

`go vet -unsafeptr=false ./...` проходит. Обычный `go vet ./...` выдаёт пять предупреждений `unsafe.Pointer` в существующей COM ABI-обвязке; те же пять есть в исходном теге 0.3.6. Полный vet не чистый.

Опциональные тесты не записывают звук и не запускают стенд без явных env-переменных:

```powershell
# ffmpeg/ffprobe должны быть в PATH; output dir — абсолютный путь вне репозитория
$env:LB_DIAGNOSTIC_DIR = 'C:\Trading\!!VB2Broadcast\.tools\my-audio-test'
$env:LB_DIAGNOSTIC_PACKET_CLOCK = '1'
go test -v -run '^TestDiagnosticNativePacketClock$' -count=1
# Снять флаг перед обычными проверками
Remove-Item Env:LB_DIAGNOSTIC_PACKET_CLOCK
$env:LB_DIAGNOSTIC_ENCODED_AUDIO = '1'
go test -v -run '^TestDiagnosticNativeEncodedAudio$' -count=1
Remove-Item Env:LB_DIAGNOSTIC_ENCODED_AUDIO
```

Тесты воспроизводят тихий контрольный тон и записывают системный звук; encoded-тест также захватывает рабочий стол. Локальные результаты: `.tools/diagnostics-0.3.6*`, `.tools/diagnostics-0.3.7-clock`, `.tools/diagnostics-0.3.7-encoded`, `.tools/codec-quality` в корне рабочего пространства.

Следующий необходимый приёмочный тест — исправленный захват на презентере и измерение кадра/звукового импульса на двух физических ПК, затем длительная работа и потери/джиттер Wi-Fi. Адаптивное управление качеством нужно строить после устранения буферизации приёмника: регулировка bitrate по heartbeat не обнаруживает очередь декодера.

## Тестовая сборка

Собран `dist/test-0.3.7-beta.1/LocalBroadcast.exe`, версия задана при сборке `-X main.appVersion=0.3.7-beta.1`; на этапе первоначальных испытаний версия основного исходника и опубликованный релиз не менялись. SHA256 EXE: `cb8aff1df9516274eb7bd069f0f5ee4482055a7a96d58a0b36697c1d033744a4`.

Пакет `dist/LocalBroadcast-0.3.7-beta.1-Update-v1-win-x64.zip` создан штатным упаковщиком/валидатором, CRC ZIP проверена. Внутри только manifest, EXE и примечания; зависимости FFmpeg не изменены. Рядом с тестовым EXE сохранены инструкция ручной проверки и копия отчёта. Сборка исправляет звук, не содержит экспериментального переключения видеокодека. На момент первоначальных испытаний на GitHub не публиковалась и на работающих ПК не устанавливалась. После испытаний версия исходника подготовлена к выпуску 0.3.7-beta.1; хеш опубликованного артефакта нужно сверять с его отдельным .sha256.
