# Интернет-обновления LocalBroadcast

## Решение и паспорт (ADR, 19.11.2026)

Использован опыт `VB2CCC/docs/guides/INTERNET_UPDATES_PLAYBOOK.md`; его команды и product ID не копируются. Продукт LocalBroadcast, Windows x64, Go single EXE с встроенным веб-интерфейсом и нативным окном. Установка per-user `%LOCALAPPDATA%/Programs/LocalBroadcast` или writable portable-папка. Настройки `%APPDATA%/LocalBroadcast/config.json` (либо явный `-config`) содержат роль, ключ, ID и маршруты; обновлятор не меняет их. OBS, его сцены, брандмауэр, FFmpeg/FFplay и их лицензии обслуживает существующий установщик.

Источник: публичные релизы `bukirev/LocalBroadcast`, клиент без PAT. Stable исключает prerelease; beta допускает оба канала и выбирает максимальную SemVer. Сеть используется только по команде. Обрыв/лимит API отображаются ошибкой. Авторизация публикации отдельна от реализации; эта задача не публикует новый релиз автоматически.

Обновление ядра заменяет **только LocalBroadcast.exe**. Полный ZIP для первой установки остаётся отдельным. Это осознанное отличие от многокомпонентного VB2CC: все собственные интерфейсы и helper уже в EXE; пересылать 329 MB на каждую правку не требуется. Изменение обязательных сторонних компонентов требует полного установщика и нового dependencySet. В этой версии dependencySet `ffmpeg-9.0.2-srt`, dataSchema=2, package/updater protocol=1. Миграции пользовательских данных через updater запрещены.

Доверие: HTTPS, фиксированный repo/CDN allowlist, SHA-256 и размер GitHub asset плюс файловый manifest. Это не независимая подпись издателя и не защита от компрометации аккаунта GitHub. Authenticode/подписанные metadata и ротация ключей пока не реализованы.

Контракт ZIP: `update-manifest.json`, `LocalBroadcast.exe`, `RELEASE_NOTES.md`. Лимиты: ZIP 32 MiB, распаковка 64 MiB, ровно три файла, без подкаталогов, symlinks, дублей/ADS. Manifest product/runtime/version/dependencySet/schema/protocol и хеши файлов проверяются до закрытия приложения и повторно helper. EXE проверяется как PE AMD64, что не заменяет доверие к издателю.

На каждом ПК: «Обновления» → канал → «Проверить» → «Скачать» → «Установить и перезапустить». Нативное окно также предоставляет проверку/загрузку/установку. Во время скачивания сервис работает. Перезапуск требует отдельного действия; для активных медиапотоков — подтверждения прерывания. На главном ПК запись/стрим OBS блокируют установку. Другие компьютеры не обновляются удалённо без участия их оператора.

Транзакция: доверенная копия текущего EXE запускается helper вне install root, подтверждает идентичность родителя, ожидает разрешение и выход именно этого процесса. Журнал записывается до rename; прежний EXE сохраняется на том же диске. Кандидат загружает конфигурацию, проверяет медиабинарники, создаёт окно и localhost UI, но не начинает обычную работу до durable commit. Неготовый кандидат до commit останавливается по собственному process handle и откатывается. После commit автоматический откат запрещён: пользователь уже мог возобновить работу. Readiness не означает аппаратную или многочасовую стабильность.

Прежний путь/ярлыки/working directory и `-config` сохраняются. Защищённый каталог без прав записи отклоняется до остановки, UAC не запрашивается. Запуск после незавершённой транзакции блокируется и предлагает recovery. Внешний helper и план остаются пригодны для восстановления даже при отсутствии основного EXE. Хранится последняя резервная версия; удаляются только известные служебные файлы завершённых операций этой установки. Неизвестные файлы и reparse points не удаляются.

Самый старый клиент встроенного updater — 0.3.6-beta. Версии 0.3.3–0.3.5 сначала вручную устанавливают 0.3.6-beta полным установщиком. Настройки сохраняются. Нельзя объявлять эти старые EXE проверенными legacy-updaters: updater в них отсутствует. Реальный переход на следующий публичный релиз будет отдельной приёмкой после публикации.

## Выпуск и проверка

Версия по умолчанию в `model.go` — источник номера. `-package-version` защищает от упаковки устаревшего EXE под новым именем. Для QA `-X main.appVersion=...` используется только в изолированных синтетических переходах, не для перепубликации существующего номера.

```powershell
go test ./...
go vet -unsafeptr=false ./...
go build -trimpath -ldflags='-s -w -H windowsgui' -o dist/LocalBroadcast.exe .
./scripts/package-windows.ps1 -Version 0.3.6-beta
# В новой package-папке лежит полный набор для существующего установщика.
# prepare-offline.ps1 добавляет оригинальные проверенные зависимости.
```

Пакет `LocalBroadcast-VERSION-Update-v1-win-x64.zip` автоматически создаётся самим EXE через production validator. Создание поверх существующего Update ZIP отвергается. Опубликованный номер/asset не исправлять перезаписью; следующий выпуск получает новый номер.

CI на теге дополнительно готовит Offline ZIP. `scripts/publish-release.ps1` требует все четыре артефакта и SHA-файлы: portable ZIP, Setup, Update ZIP, Offline ZIP. Сначала создаётся draft; каждый remote asset сверяется с локальным размером и SHA-256, включая digest GitHub. Без `-Publish` скрипт оставляет проверенный черновик. В этой задаче публикация не запускалась.

После согласованного выпуска проверить анонимным клиентом discovery и загрузку, затем реальным сохранённым updater 0.3.6-beta выполнить переход на опубликованную следующую версию. Сохранить старый EXE/helper и его SHA-256 для будущей совместимости. Проверять синтетическими данными, не во время мероприятия.

Первичные контракты: [GitHub Releases API](https://docs.github.com/en/rest/releases/releases), [release asset download/digest](https://docs.github.com/en/rest/releases/assets), [SemVer](https://semver.org/), [gh release create](https://cli.github.com/manual/gh_release_create), [gh release edit](https://cli.github.com/manual/gh_release_edit).

## Восстановление и обслуживание

Состояние замены: `INSTALL/.lb-update/journal.json`, резервная версия `backup-ID.exe`. Внешний helper/план находятся в пользовательском cache `LocalBroadcast/Updates/INSTALL-ID/TRANSACTION-ID`, отдельно для каждой установки. Основной EXE не запускает обычную работу при незавершённом журнале. Используйте `INSTALL/.lb-update/Recover.cmd`: он запускает сохранённый доверенный helper, который повторяет проверку плана и откат. Если кандидат ещё ждёт commit, дайте ему до 30 секунд завершиться. Если файл занят посторонним процессом, восстановление оставляет журнал/backup и сообщает об ошибке.

Rollback до commit возвращает прежний EXE и запускает его с тем же `-config`, портом и рабочей папкой. После commit recovery не откатывает автоматически работающую версию. Для намеренного понижения после успешной работы требуется отдельная операторская процедура, которую эта версия не автоматизирует.

Успешно использованный ZIP удаляется. При следующем последовательном успешном обновлении известные файлы предыдущей завершённой операции убираются, последняя предыдущая версия остаётся. Отмена удаляет только принадлежащую загрузке проверенную копию; чужие файлы сохраняются. Незавершённые/неудачные операции и старые резервные копии после сбоя могут сохраняться для диагностики — полного автоматического ограничения их объёма пока нет. Рекурсивная очистка неизвестных папок не используется.

Readiness означает: правильный EXE/версия/nonce/PID, загруженные существующие настройки schema 2, созданное окно, связанный localhost HTTP listener, наличие FFplay и проверенная поддержка SRT FFmpeg. Это не проверка сетевых маршрутов, OBS-сцен, камеры или качества звука. До durable commit отсутствуют рабочие потоки и запись настроек. После commit автоматический rollback запрещён даже при ошибке финального `running`-подтверждения.

`-ui-port` и отдельный `-config` позволяют проверять экземпляр изолированно от рабочей установки. Тестовые переменные `LB_UPDATE_TEST_NO_UI`/`LB_UPDATE_TEST_OFFLINE` применяются только harness к своим дочерним процессам; в обычном запуске они не задаются. Веб-панель блокирует установку при несохранённых правках своей вкладки; нативное подтверждение напоминает сохранить изменения в браузере.
